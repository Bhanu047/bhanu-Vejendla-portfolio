ENGINEERING NOTE · BATCH RECOVERY

A batch is finished only after its output commits.

A manifest lets monthly backfills pick up where they stopped, as long as it’s accurate. I set up the load so a failed month gets retried, and a successful retry replaces only that month’s partitions.

System
PySpark bronze → silver → gold
Unit of work
One source month
Validation
49 offline tests

01 · WHAT CAN GO WRONG

The manifest can say “done” before the data is there.

The pipeline loads one month at a time and keeps a JSON manifest so it can skip months that are already done. The risky order is marking a month complete before its gold output is safely written.

If the job crashes between those two steps, the next run trusts the manifest and skips a month that never finished. The rerun looks fine, but the data has a hole in it.

02 · THE WRITE

Overwrite only the partitions a month touches

Each month can span several pickup_date partitions. With dynamic partition overwrite, only the dates in the current batch get replaced. Partitions from other months are left alone.

So rerunning a month always gives the same result. It rewrites its own dates and doesn’t add duplicates or delete other months’ data.

spark.conf.set(
    "spark.sql.sources.partitionOverwriteMode",
    "dynamic",
)

frame.write.mode("overwrite") \
    .partitionBy("pickup_date") \
    .parquet(target)

03 · THE COMMIT

Update the manifest only after gold is written.

A month goes into the manifest only after the final gold write finishes. If anything fails before that, the month isn’t recorded and the next run picks it up again.

The manifest itself is written to a temporary file and then renamed, so a crash mid-update can’t wipe out the last good version. Between the write order and the atomic rename, the next run knows exactly where to resume.

  • Write and validate bronze, silver and gold outputs.
  • Leave the month unrecorded if any stage raises an error.
  • Swap in the new manifest only once it’s fully written.
  • Skip a month only if the saved manifest says it finished.

04 · WHY PLAIN PARQUET

Why I didn’t use Delta Lake here

I left out Delta Lake and Iceberg on purpose so the recovery logic stays visible. That means the manifest and partitioning do work that a transactional table format would normally handle for you.

For a monthly pipeline of this size, that keeps it easy to read and test. With more data or several writers at once, I’d switch to a transactional table format but keep the same rule: only mark a month done after its data is committed.

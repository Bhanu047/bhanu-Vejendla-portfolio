ENGINEERING NOTE · SHARED STATE

When two teammates save at the same time.

When several people edit the same screen, one person’s save can quietly wipe out someone else’s. A single-user form never has that problem. Kingdom846 rejects the out-of-date save and lets the user decide what to do next.

System
React → Express → SQLite
Risk
Silent last-write-wins
Response
HTTP 409 Conflict

01 · THE PROBLEM

Two people with access can still overwrite each other.

Several teammates use the War Room and can have the same roster open at once. Say both load version 12. One saves, which creates version 13, while the other is still editing version 12.

A plain update statement would accept both saves. The second one would look like it worked, even though it was built on old data, and the first person’s changes would be gone with no warning.

02 · THE FIX

Send the version with every save.

Every read returns the current version. The client sends it back with the update, and the server checks it against the stored version as part of the write.

If they match, the update goes through and the version moves on. If they don’t, the server returns a conflict and leaves the record alone. This is optimistic concurrency. Editing stays fast, and an out-of-date client can’t quietly overwrite newer work.

client version == stored version
    → save changes and increment version

client version != stored version
    → return 409; do not write

03 · WHAT THE USER SEES

Telling the user what happened

A 409 protects the data, but on its own it just looks like an error. So the interface says a newer version exists and shows the latest save, so the person with the old copy knows what happened.

  • Load the latest version and carry on from the teammate’s changes.
  • Review the difference before trying the edit again.
  • Overwrite the current version only if the user explicitly chooses to.
  • Never show a rejected save as if it worked.

04 · WHAT IT DOESN’T COVER

Version checks don’t replace permissions.

A version check tells you whether an edit is up to date. It says nothing about whether the user is allowed to make it. Kingdom846 checks roles on the server too, so a client can’t give itself more access by tampering with a request.

So there are two separate checks: identity and role decide who can write, and the version decides whether a particular write is safe to apply.

ENGINEERING NOTE · STREAMING RELIABILITY

Exactly-once is won in the sink.

After a failure, a Spark checkpoint can replay the last micro-batch. I found out the hard way that recovery is only safe if writing the same batch twice leaves the same data on disk.

System
Kafka → Spark → Parquet
Signal
3,091 rows in · 926 on disk
Validation
52 automated tests

01 · WHAT BROKE

The job looked healthy while rows went missing.

My first sink partitioned output by event date and overwrote whichever partition a micro-batch touched. The unit test only wrote one batch, so it passed. Once the stream was running, the problem showed up: every batch for today landed in the same date partition, and each write wiped out the one before it.

A simple count settled it: 3,091 records went in and 926 were left on disk. The write strategy looked fine on its own, but it was losing data.

02 · THE FIX

Give each micro-batch its own output path.

The checkpoint tracks which source offsets Spark has processed, but after a crash the last batch can still run a second time. So the sink has to cope with the same write arriving twice.

I changed the path so each batch writes under its own batch=<id> prefix. If batch 7 is replayed, it overwrites batch 7 and nothing else. Later batches get their own prefix, so they can’t touch earlier output. Event date is still there as a nested partition, so queries can prune on it.

target = Path(path) / f"batch={batch_id}"

(
    frame.write.mode("overwrite")
    .partitionBy("event_date")
    .parquet(str(target))
)

03 · HOW I TESTED IT

Testing what happens on replay

Checking that a config flag is set doesn’t tell you much. These tests check the data that actually ends up on disk after the failures this pipeline is meant to handle.

  • Write the same batch twice; the row count should stay the same.
  • Write later batches for the same event date; the earlier rows should still be there.
  • Send good and malformed records through the fan-out writer, replay the batch, and check that neither destination gets duplicates.
  • Run several batches in a row and check that every one of them is still there.

04 · WHAT IT COSTS

The catch: lots of small files.

Writing per batch means the file count keeps growing. For this project I’m fine with that, because safe recovery matters more. In production I’d either compact files on a schedule or move the sink to Delta Lake or Iceberg and use transactional merges.

“Exactly-once” only holds when source offsets, checkpoints and the sink all agree. Getting the checkpoint right wasn’t enough on its own.

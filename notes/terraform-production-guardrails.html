ENGINEERING NOTE · INFRASTRUCTURE SAFETY

Asking for force-destroy is not the same as receiving it.

I didn’t want production safety to depend on someone remembering the right setting. In this Terraform module, production buckets can’t be force-destroyed, even if the caller asks for it.

Platform
AWS data lake
Production rule
force_destroy is always false
Validation
Mocked Terraform plan

01 · THE RISK

One flag can let Terraform delete a full bucket.

Terraform’s S3 force_destroy setting lets you delete a bucket that still has objects in it. That’s handy in a throwaway development environment and dangerous in a production data lake.

If the same Boolean is exposed in every environment, production is only as safe as a variable file, a command-line override or someone in a hurry. Terraform will accept the setting even where it should never be allowed.

02 · THE GUARDRAIL

Let the environment decide the real value.

The module keeps the requested value separate from the value the resources actually get. In development the input is used as given. In production it always comes out false.

force_destroy_effective = (
  var.environment == "prod"
  ? false
  : var.force_destroy
)

It also rejects unknown environment names, so a typo can’t fall through to a permissive default.

03 · HOW I TESTED IT

Testing the case that should be refused

The most useful test passes in the bad combination on purpose: production plus force_destroy = true. A mocked provider lets Terraform plan without AWS credentials, and the test checks that the effective value is still false.

run "prod_refuses_force_destroy_even_when_asked" {
  command = plan

  variables {
    environment   = "prod"
    force_destroy = true
  }

  assert {
    condition = output.force_destroy_effective == false
  }
}

04 · WHAT IT DOESN’T PROVE

A mocked plan only tests the configuration.

The tests also cover least-privilege rules, like stopping the pipeline role from writing raw data and not using wildcard IAM actions. They run fast because the AWS provider is mocked.

The downside is that they only check the planned resources and the policy logic. Nothing gets deployed to AWS. The next step would be to apply the stack in a sandbox account and run live permission checks before promoting it.
